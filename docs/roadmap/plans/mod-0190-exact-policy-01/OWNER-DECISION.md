## D190-05 — exact proposed receipt/replay/correlation policy

| Case | Frozen fact | Single proposed behavior and acceptance example | Classification |
|---|---|---|---|
| Receipt identity | Three POSTs require `Idempotency-Key` (`#/components/parameters/IdempotencyKey`), but tuple/TTL are unspecified. | Unique durable tuple **(TenantId, LegalEntityId, operationId, targetId-or-create-sentinel, exact parsed key string)**. Create has sentinel; snapshot/sign-off target is sandopPlanId. Actor and correlation are not key components. No TTL/key recycling in isolated slice. Same key on two plans is independent; same create key in one scope is not. | Internal **clarification proposal**; no wire change by itself. |
| Fingerprint | Request schemas have `additionalProperties:false`; no fingerprint rule. | Hash canonical **decoded JSON structure**: object member order/escapes normalized; array order significant; string values exact Unicode scalar sequence; omission and explicit null distinct (null rejected where schema forbids); no trimming/case folding; include operation and target in tuple, not fingerprint; exclude correlation and actor. `name:" A "` and `name:"A"` differ. | Internal **clarification proposal**; test malformed/body validation before receipt lookup, so invalid requests cannot retrieve a prior success. |
| Same key+same payload | Pack §13 promises original replay; frozen response schemas do not expose an `idempotentReplay` field. | Return the **stored original status and body** (201 for the three POSTs) with no new aggregate, snapshot, sign-off, receipt, audit, event or DEMAND/Workflow read. `X-Correlation-Id` on this response is the **current valid request** UUID because header description says echoed request; stored event/audit keep original UUID. Example: original corr A, retry corr B → original plan ID/body, header B, one event with corr A. | Replay itself is **pack clarification**; original/current correlation split needs **operation-level published clarification** before HTTP oracle, and consumer consent if header semantics change. No replay marker added to body. |
| Changed valid payload | Frozen create/snapshot/sign-off each declare 409, but their 409 codes are business conflicts only. | Same tuple/key, changed valid fingerprint → **409 `IDEMPOTENCY_KEY_REUSED`**, current correlation in error body/header, zero new writes/reads. Receipt lookup precedes business duplicate/state re-evaluation for valid requests. Example same key create with changed name → this code, not plan-already-exists. | **Versioned wire-visible amendment**: add code/example to all three POST 409 responses and document precedence. Do not implement before publication/consent. |
| Concurrent/unknown commit | No frozen transaction/recovery algorithm. | Concurrent identical same-key requests resolve one commit and original-result replay; receipt/aggregate/audit/outbox commit atomically. Definite precommit fault rolls all back. Unknown commit: inspect durable receipt; if found return original, otherwise return an explicitly documented retryable failure, never claim zero writes solely from unknown result; same-key retry after restart recovers. | Internal **clarification proposal**; exact retryable HTTP status/code for unresolved unknown commit is **amendment candidate**, because operation failures do not declare 503. |
| Correlation validation | Required `X-Correlation-Id` has UUID format; success/error `X-Correlation-Id` descriptions say echo request (`#/components/parameters/CorrelationId`, `#/components/headers/CorrelationId`, `#/components/schemas/Error`). No duplicate/missing fallback contract. | Valid correlation is an HTTP request trace, not plan identity. Missing/malformed/duplicate correlation: proposed **400 `INVALID_CORRELATION_ID`**, no write/receipt; server creates a rejection-only UUID and uses it consistently in response header/body when no single valid request UUID can be echoed. Duplicate ID header cannot be silently joined. | **Versioned wire-visible amendment** to each operation's 400 response and echo/fallback rule. Authentication parser 401 remains distinct; this proposal does not override it. |
| Header/name input width | Key schema: string `minLength:1`, no max/trim. Create name schema: string `minLength:1`, no max/trim (`#/components/schemas/CreateSandopPlanRequest`). | Accept every schema-valid nonempty parsed key and nonempty name, including >200 characters and leading/trailing spaces; preserve exact values for uniqueness/fingerprint. Example 201-character key and `" A "` name must not be rejected **because of 200/trim**. Generic transport body/header limits are separate, not a new business rule. | **Clarification correcting draft pack §4/§12**. Choosing trim or max 200 instead requires versioned schema amendment and existing-consumer compatibility review. |

**Precedence proposed:** authentication parser → trusted tenant/LE/grant → correlation/key syntax and request schema → scoped receipt lookup → changed-fingerprint 409 or original-result replay → plan/snapshot state and uniqueness → atomic commit. A wrong-scope plan never leaks a receipt. Authenticated but unauthorized replay remains 403 before receipt. For a valid same-key replay after the plan later changes state, receipt wins and returns original 201. For a different key, current state/duplicate rules apply. This ordering is proposed, not published.
