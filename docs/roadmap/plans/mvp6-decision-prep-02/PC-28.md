# PC-28 — API profile: the verifier's non-Platform `direct-gateway` default vs Shipment's same-origin MVC (UI183-A01)

**NOT APPROVED — prepared text only.** Queue Q12 · decides: owner, as the shared frontend quality-gate owner, together
with the MOD-0183 owner. The integration owner is involved only under option B. Present this after DN-02.

## Owner question

Should the Shipment DataTable be verified under the existing `proxy-profile`? That profile checks for same-origin
`/SupplyChain/Shipments/api` and no direct browser calls to the Gateway, which is exactly what UI183-A01 requires.

**Recommended answer: A — yes. The existing profile is selected; no verifier change is needed.**

## Current state (checked 2026-09-26) — new finding

- **Still needed as a decision, but smaller than the proposal assumed.**
  - The standard workflow `.antigravity/workflows/quality-gate-datatable.md` (`2c4801e8…`) already requires the profile
    to be chosen explicitly (line 31). It defines `proxy-profile` as a browser endpoint of `/{AreaName}/{ModuleName}/api`
    with no direct `:5000` calls (line 32), plus controller-to-Gateway proof (line 142).
  - The mandatory static guard is run with `--api-profile proxy|direct-gateway` (line 151).
  - `verify_datatable_page.py:418-434` only *defaults* non-Platform areas to `direct-gateway` when no profile is given.
- **Rerun today on the exact A12 composition.** The accepted `index.js` (`97f8f2a5…`) line 4 is
  `const endpoint = '/SupplyChain/Shipments/api';`. The two runs:
  - default (`direct-gateway`): 49 PASS / 35 FAIL, including FAIL 28 (`window.API` service base);
  - `--api-profile proxy`: **51 PASS / 34 FAIL**. FAIL 28 is gone, and two proxy checks PASS: "index.js uses same-origin
    frontend proxy endpoint (/SupplyChain/Shipments/api)" and "proxy profile avoids direct browser Gateway calls". The
    other 34 FAILs are identical.
  - Evidence: `evidence/verifier-a12-direct-gateway.txt` and `evidence/verifier-a12-proxy.txt`.
- The proposal's recommended ruling (a Shipment same-origin-MVC profile) is therefore available as the existing
  `proxy-profile`, and needs no verifier change.

## Options

| Option | Effect on scope | Effort (O/M/P) | Risk |
|---|---|---|---|
| **A — Declare Shipment a `proxy-profile` DataTable (recommended)** | The static guard runs with `--api-profile proxy`, and the browser network must show only same-origin `/SupplyChain/Shipments/api`. The controller's configured `GatewayUrl` target is inspected (`SupplyChainShipmentsController.cs` lines 34–35 and 63 in the A12 source), and any browser request to a Gateway or service port fails. Matches A01 unchanged. | Negligible; it is part of the A14 VER. | Low. Uses an existing, documented profile. |
| B — Amend A01 to direct-Gateway browser traffic | Needs explicit MOD-0183, integration-owner and security-owner approval, plus new CORS, auth and browser acceptance. | UNESTIMATED. | High. Reverses an accepted transport boundary. |

**Reason for A:** A01's same-origin rule is already a standard profile in the quality gate. The generic FAIL 28 came only
from the tool's default, not from a rule the Shipment UI breaks.

## Exact decision text (NOT APPROVED — prepared text only)

> PC-28 için MOD-0183 Shipment DataTable sayfasının `proxy-profile` (same-origin MVC) olarak doğrulanmasını onaylıyorum: `.antigravity/workflows/quality-gate-datatable.md` satır 31–32, 142 ve 151 uyarınca statik guard `--api-profile proxy` ile çalıştırılır; browser trafiği yalnız same-origin `/SupplyChain/Shipments/api` olmalı, MVC controller'ın yapılandırılmış `GatewayUrl` (Gateway) hedefi kod/log ile doğrulanmalı ve browser'dan Gateway/servis portuna giden her istek profili FAIL etmelidir. UI183-A01 değişmez. Varsayılan `direct-gateway` ile alınan tarihsel generic sonuç (49 PASS / 35 FAIL, FAIL 28 dahil) korunur; `--api-profile proxy` sonucu (2026-09-26 yeniden çalıştırma: 51 PASS / 34 FAIL) onun yanında kaydedilir. Bu karar `.antigravity` kural/verifier değişikliği, waiver, repo-geneli PASS, CORS veya transport değişikliği yetkisi vermez.
