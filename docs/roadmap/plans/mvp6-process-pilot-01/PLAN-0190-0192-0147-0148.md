# Plan — MOD-0190, MOD-0192, MOD-0147, MOD-0148

> Written 2026-10-05. The four MVP-6 modules with no runtime code. They are blocked for
> **two entirely different reasons**, and treating them as one backlog is the mistake to avoid.

## A. MOD-0190 S&OP · MOD-0192 Capacity — a capability gap

### What is actually true

Both packs are `shell: tenant` with approved UI scope and self-registration (2026-09 owner
decisions), and both have a v3 UI draft. Their service code exists. They are **not** composed,
and Q381 made that honest: their routes answer 404, not 500.

**The fixture reader is not a defect — it is what the packs specify.** MOD-0190 §42 and
MOD-0192 §41/§117 scope this slice to *"exact tenant/LE-scoped test-only DEMAND
ID/version/checksum fixtures"* with *"no live DEMAND/constraint HTTP call in this slice"*.
Q273 read the empty fixture collection in a composed host as the blocker; the pack had
already chosen fixtures for the slice. The gap only appears when you try to compose them
for real use.

### The real gap, measured

`DEMAND` v1 is FROZEN, owned by MOD-0188, and offers two operations:

```
GET /plan?itemId={uuid}&period={YYYY-MM}
  → planId, itemId, period, quantity, uomId, confidence, status, contractVersion
GET /forecast
```

Both modules ask `MatchesAsync(scope, planId, version, checksum)` — **lookup by plan
reference**. DEMAND looks up **by itemId + period** and *returns* a planId. The response
carries no plan version (`contractVersion` is the contract's own version) and no checksum.

So DEMAND v1 cannot answer the question, and Q282's ruling — *impossible as framed, not
expensive* — stands. CT doubted it on a word count today and the operation text restored it.

### The three ways out, and what each costs

| | what it is | who decides |
|---|---|---|
| **1. DEMAND v2, additive** | one operation that resolves a plan reference: planId + version + checksum → published/not. Extension is additive under K16, so v1 consumers are untouched. | **MOD-0188 owner**, in MVP-4 scope |
| **2. Narrow what the modules ask** | drop checksum, or resolve by itemId+period and compare. Changes two frozen module contracts and weakens the immutable-provenance guarantee both packs are built on | MOD-0190 / MOD-0192 owners + CT |
| **3. Stay fixture-bound** | what the packs already say for *this slice*. Honest, and it means these two modules never run on real demand data in MVP-6 | owner, as a scope statement |

**Option 3 is the status quo and nobody has written it down as a decision.** That is the
first thing to fix: either it is the plan, or it is not.

### Sequence, once a way out is chosen

```
decision (1, 2 or 3)
        ↓  only for 1 and 2

        ↓
compose the module in Program.cs, remove its MediatR exclusion
        ↓
its guard exception entry FAILS and comes out (that is the design)
        ↓
build the UI from the v3 draft — DO NOT SHIP IT UNCHANGED
        ↓

```

⚠ The v3 drafts carry the per-payload idempotency key (R-3 measured it at Capacity
`details.js:616`, S&OP `details.js:510`). Three earlier drafts were each declared complete —
one of them CT ACCEPTED — and each shipped with five or six defects, 15 to 18 files changed.
