## Common transport, error, receipt and precedence proposal

All twelve operations require bearer authentication and a single valid UUID `X-Correlation-Id`. The three S&OP and three Capacity POSTs require a nonempty parsed `Idempotency-Key`. Key identity is **exact parsed string**: no trim, case folding, max-200 rule or silent Unicode normalization. `CreateSandopPlanRequest.name` likewise retains its frozen minimum length 1 with no new trim/maximum; a 201-character key or name is not rejected solely for length. Standard host request-size limits are separate transport limits. The body remains the frozen schema with `additionalProperties:false` where declared. No new endpoint or body field is introduced.

Precedence candidate: authentication parser (401) → trusted tenant/LE and operation grant (403) → required headers/body schema (400) → scoped target existence (404) → durable receipt identity/fingerprint → current state/duplicate/fixture validation (declared 409/422) → atomic commit. Cross-scope target is 404 and cannot expose a receipt. A valid same-key receipt replays before a later state change or fixture reread; changed valid payload is 409 `IDEMPOTENCY_KEY_REUSED` before current business conflicts. Invalid payload never retrieves an old success. Reads have no receipt. All failures leave no new write, except unresolved unknown commit, whose result is unknown until durable receipt resolution.

Receipt tuple: `(TenantId, LegalEntityId, operationId, targetId-or-create-sentinel, exact parsed key)`. Actor and correlation are excluded. SHA-256 fingerprint is over canonical decoded JSON: object member order/escape spelling normalized; array order and exact Unicode string/decimal lexemes retained; omitted and null distinct (null rejected if schema forbids); operation/target are in tuple. No TTL/key reuse in the bounded slice. A different authorized actor can replay the original result without rewriting original audit actor. No `idempotentReplay` field or new response body shape is added.

Identical valid same-key request returns the stored **original status/body** (201 for create/capture/sign-off/scenario, 202 for evaluate) without dependency reread or second aggregate/receipt/audit/outbox/job. Response `X-Correlation-Id` is the **current request's** valid UUID; original persisted audit/event correlation stays original. An error generated now carries current UUID in `Error.error.correlationId` and header. A retry with a different correlation but identical payload therefore gets original business body and current header. Auth failure happens before receipt. Missing/malformed/duplicate correlation proposes 400 `INVALID_CORRELATION_ID`, no write, and one generated rejection-only UUID in response header/body because no unique valid request UUID can be echoed; this is a proposed explicit exception to the old echo description. Parser-level malformed wire bytes may be rejected before application body; they must not be called an application-envelope PASS.

Response shape for all application errors: frozen `#/components/schemas/Error` (`{error:{code,message,correlationId,details?},contractVersion:'v1'}`); success bodies and their required/null rules remain unchanged. New 401 includes `WWW-Authenticate: Bearer`; 403 is `FORBIDDEN`. Generic malformed body/header is 400 `INVALID_REQUEST`. Dependency/storage failure is 503 `DEPENDENCY_UNAVAILABLE`. For mutation uncertain commit, query durable receipt first: found → original result; unresolved → 503 `COMMIT_RESULT_UNRESOLVED` and same-key recovery after restart; never assert zero writes from the 503 alone. Known precommit failure rolls aggregate/receipt/audit/Pending outbox back. GET storage failure can use 503 `DEPENDENCY_UNAVAILABLE`, never the mutation-only unknown-commit code. Exact code/message text in candidate YAML examples is proposed, not published.

## Lifecycle/fixture boundary that candidate wire errors depend on

0190: Create Draft/null; capture from Draft or InReview appends immutable snapshot and sets InReview; sign-off only InReview against any same-plan snapshot, one decision per snapshot/role, no automatic plan Approved/Rejected even after all five roles approve. The new sign-off state-conflict code needs owner and contract release. 0192: Capacity plan/scenario remain Draft in this bounded slice; evaluation alone may progress Accepted→Running→Completed/Failed under a **separately approved** module-owned executor. The C192 proposal of startup+10-second scan, 30-second fenced lease and three attempts remains unapproved in inspected records. Terminal values come only from the exact fixture oracle `CAPACITY-EVAL-FIXTURE-192-01@1`; no live optimizer, supply-constraint source or Event Bus publisher. A Pending outbox event is written at terminal commit, no publisher delivery claim. With no approved executor, terminal E4 acceptance remains HELD.

The four approved scope limits are respected: exact tenant/LE test fixture for DEMAND with no producer endpoint; local trusted JWT actor/no Workflow; atomic Pending outbox/no publisher; Capacity fixture references/literal results only. A fixture PASS is not live DEMAND version/checksum or constraint producer validation. New 400/409/422/503 cases and the exact executor/lifecycle/replay policies are candidate amendments, not an assertion that those later proposals had already been approved.
