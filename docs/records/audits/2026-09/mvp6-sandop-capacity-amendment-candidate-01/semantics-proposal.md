The proposed 422 checksum case applies only to requests that contain `sourceChecksum` (0190 snapshot capture and 0192 plan creation). It compares against an exact **scoped test fixture**, not DEMAND v1 producer data. An unknown, stale, cross-scope or resource/period/UoM-incompatible fixture constraint yields proposed 422 `INVALID_CONSTRAINT_REFERENCE` before scenario/evaluation persistence. No new DEMAND or constraint endpoint is proposed. A different key racing for one active evaluation retains frozen 409 `EVALUATION_ALREADY_ACTIVE`; same key and changed valid payload uses proposed 409 `IDEMPOTENCY_KEY_REUSED` instead.

All candidate error examples use the existing `{error:{code,message,correlationId},contractVersion:v1}` body and UUID `X-Correlation-Id` header. A single valid request UUID is echoed in response header/body, including replay. For missing, malformed or duplicate correlation headers, a server-generated **rejection-only** UUID appears in both; it is not a persisted business root. A 503 unresolved commit is retryable only with the **same** idempotency key; it does not prove rollback. If a durable receipt is found, return the stored original 201/202 status and business body; audit/outbox keep the original correlation, while the replay response header uses the current request UUID. No success-body field is added.

## Approved internal design, subject to publication and dispatch gates

- **0190 lifecycle:** create Draft/null; capture Draft or InReview → InReview with new immutable snapshot; Approved/Rejected/Archived capture gets existing 409. Sign-off only in InReview on any same-plan snapshot, including an older one; one role decision per snapshot; trusted JWT actor/time; no automatic quorum, approval/rejection transition or invented status event. Other statuses remain representable but are not produced by this slice.
- **Both modules replay:** unique receipt tuple `(tenant, legal entity, operationId, target-or-create-sentinel, exact parsed Idempotency-Key)`. No trim/case fold or 200-character narrowing. Fingerprint canonical decoded JSON structure, including exact string values and array order; trace and actor excluded. Authenticate/authorize/validate before scoped receipt lookup. Same tuple/fingerprint replays original result with no second dependency read or write. Changed valid payload gets the candidate 409. Receipt, aggregate/state, audit and Pending outbox commit atomically. No publisher/worker or Event Bus delivery claim.
- **0192 constraint/evaluation:** exact test-only `CAPACITY-EVAL-FIXTURE-192-01@1` maps `(tenant, LE, source, constraintId, sourceVersion)` to one resource/period/UoM; only fixture references are stored. Plan and scenario remain Draft. Evaluation progresses Accepted→Running→Completed/Failed. Durable module-owned executor scans at startup and each 10 seconds, claims by status/version CAS with a 30-second fenced lease and at most three attempts; expired lease is reclaimed. Deterministic input rejection or exhausted attempts ends Failed. Terminal result is the literal fixture oracle; no general Finite/Infinite algorithm is asserted. Terminal state, timestamp and one `capacity.evaluation.completed.v1` Pending outbox record commit atomically; original submit correlation and scenario-created causation are retained. This evaluator is distinct from the excluded Event Bus publisher.
