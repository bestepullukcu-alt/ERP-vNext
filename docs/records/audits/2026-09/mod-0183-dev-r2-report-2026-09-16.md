## Root causes and exact fixes

### VER-01 — decimal digit semantics

.NET regular-expression digit classes accepted Unicode decimal digits, while
the frozen JSON Schema pattern's ECMAScript digit class is ASCII.
ShipmentLineValidator now explicitly uses [0-9] for each digit position.
Sign, integer and fractional structure remain unchanged; no positivity rule or
new quantity conversion was introduced. Frozen contract bytes are unchanged.

Direct tests cover ASCII integer/fraction, negative and leading-zero forms,
Arabic-Indic, Persian, full-width and mixed digits, and invalid exponent/sign/
fraction forms. Real HTTP tests verify Unicode quantities return 400 and leave
shipment, receipt, history, audit and outbox empty, followed by successful
ASCII 30.000 creation/reload.

### VER-02 — Unicode scalar length

FluentValidation MaximumLength counted UTF-16 code units. The shared, bounded
ShipmentNoteRules.IsWithinLength now enumerates Unicode scalars, stopping after
1000. Both transition and POD validators use that rule; null remains valid.
No change to recipient, evidence, lifecycle, scope or replay behavior.

Direct tests cover null/empty, BMP, supplementary characters, combining marks
and mixed BMP/supplementary strings. This distinguishes code points from both
UTF-16 units and grapheme clusters. Separate transition/POD HTTP tests reject
1001 supplementary code points with 400, compare complete snapshots of all five
collections, then reuse the same idempotency key successfully with 1000.
Accepted notes persist exactly in history/POD.
