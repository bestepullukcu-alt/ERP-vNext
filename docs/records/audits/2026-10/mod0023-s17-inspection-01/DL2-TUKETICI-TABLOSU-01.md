## 0. What the engine does now (read from the index)

- **Start** (`StartWorkflowInstanceHandler.cs`): `Handle` looks the key up first; if an instance exists it goes to `ExistingStartResponseAsync`, which calls `SameStartFactsAsync` BEFORE anything else, whatever the instance status is now. Compared facts: template (resolved id), ObjectType, ObjectId, ObjectRef, **starter** (`StartedByUserId == current user`, else `StartedBy` name), and, when the instance carries a `StartRequestFingerprint`, the SHA-256 of `template | objectType | objectId | objectRef | sorted normalized candidates | ReasonCode (trimmed) | CommentRequired | EvidenceRequired | DueAt.UtcTicks`. Different -> 409 `WORKFLOW_INSTANCE_START_CONFLICT`. An instance written before BL-549 has no fingerprint: it is held to template/object/ObjectRef/starter only (so a changed DueAt or candidate list on a legacy half start does NOT 409).
- **Not in the fingerprint**: `DisplayContext` (title/subtitle/chips/deep link). Changing it never 409s.
- `idempotentReplay` is a trailing optional field of `StartWorkflowInstanceResponse`. No consumer read in this task reads it (grep: only SupplyChain has its own unrelated `IdempotentReplay`).
- **Transitions** (`WorkflowTaskTransitionSupport.BuildBodyBoundIdempotentResponseAsync`): order is actor check (`ActorId` and `ActorRef` of the stored log must equal the caller -> else 403 `WORKFLOW_ACTOR_DENIED`), then body (`WorkflowTerminalTransitionWriter.SameBody`: reason, comment, evidence, signature (Approve only), RequestInfo target; ordinal, null vs "" differs) -> else 409 `WORKFLOW_TRANSITION_IDEMPOTENCY_CONFLICT`, then the recorded answer (200 isIdempotent). Approve/Reject/RequestInfo/Cancel use it; Delegate keeps the old actor-only check. For Approve/Reject/RequestInfo the other-actor answer was already 403 before this change; **Cancel** is the one whose other-actor answer changed (200 -> 403).
- **Late twin**: only `TransitionAsync` (Approve/Reject) and `RequestInfoAsync` re-read the key. `CancelAsync` has no late-twin re-read (diff: not touched), so a concurrent cancel twin still gets 409 `WORKFLOW_TASK_INVALID_STATE` when the key lookup ran before the twin committed.
- Atomicity (inference from `CommitAsync`/`CommitTransitionAsync`): when Platform transactions are configured, task + instance + log commit in one transaction, so "log row exists but the task is still open" does not arise in production; it can arise only in in-memory doubles. This is why most consumers cannot reach the new answers by retrying.
- The HTTP controller binds the actor from the token (`TryBindActor`; a body `actorId` that differs from the token `sub` is 403 `WORKFLOW_ACTOR_MISMATCH`, a different code). The body key (`idempotencyKey`) is what the engine uses; the `Idempotency-Key` header that Web/Gateway forward is not read by the generic workflow endpoints (grep: only `TrustedWorkflowConsumerRequestExecutor` and `BusinessReferenceDataController` read it).

## 2. Findings that need a decision

1. **Inventory quarantine submit is the one production path where the same key is re-sent with facts that can change** (row 8a). Key is one per decision (`...:r1`), a `StartFailed` decision is resubmittable, and candidates and due date come from editable company settings. If the first start committed but was reported as failed and the settings changed, the decider gets 400 `WorkflowRejected` on every resubmit while an orphan instance sits in the approver's inbox. Decide: key suffix for a resubmit round, or map START_CONFLICT to a readable state, or accept and document.
2. **Task Center key is actor-, text- and signature-free** (row 7): `wcn-action-v1:` + hash(provider, item, action, version). A lost response followed by a re-entered reason or a new e-signature now answers 409 `WORKFLOW_TRANSITION_IDEMPOTENCY_CONFLICT` (before: recorded 200) although the decision already landed. The frontend has no entry for the new code (it only logs "unmapped 409" and shows a generic toast, no reload). Decide: map the code and reload on it, or include text/signature in the key, or accept.
3. **Tasks due-date case** (row 4) is handled by supersede+restart for approval and review, but no caller-level test changes `DueAt`; the upward request cannot hit it. A concurrent-edit race with no half start (`halfStartKey` null) returns 409 and is only logged. Decide: add the DueAt case to the supersede theory.
4. **CRM and MDM start** (rows 9a, 10a): a different person submitting after a lost record write now gets 400 instead of silently adopting the first person's instance. Looks intended (K1); no consumer test.
5. **Web console** (row 11a): the key survives failed attempts and is editable, so edit-and-resend after an unseen commit now 409s; a Cancel ACTOR_DENIED 403 is shown as "Permission missing". Decide: wording only.
